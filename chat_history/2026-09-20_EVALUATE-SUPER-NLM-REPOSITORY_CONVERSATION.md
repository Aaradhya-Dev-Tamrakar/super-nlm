# 3. Account rotation is probably the most technically interesting subsystem

`mcp_server/rotator.py` is more sophisticated than the typical multi-account implementation.

It tracks:

```text
global dispatch counter
per-profile inflight count
burst cooldown
daily quota cooldown
conversation ownership
success/error statistics
shared notebook cache
```

And the selection algorithm combines:

```text
eligibility
   ↓
Pro filtering
   ↓
explicit exclusions
   ↓
cooldown filtering
   ↓
minimum in-flight load
   ↓
round-robin selection
```

That is a sensible load-balancing model for your specific use case.

The tests also demonstrate that you thought beyond nominal rotation:

- six-node round-robin
- Pro → Pro 429 failover
- inflight balancing
- multi-turn session pinning
- fleet health
- MCP registration

That is considerably stronger than simply doing:

```python
accounts[current % len(accounts)]
```

### One caveat

There is a semantic mismatch in the implementation.

`synthesize_cross_notebook()` accepts:

```python
synthesizer_profile_id
```

but the actual Gemini synthesis call ultimately uses:

```python
synthesize_with_gemini(question, sub_results)
```

and does **not** use the supplied profile ID/API credential to select the synthesizer.

Instead it searches the profiles for:

```python
p.isDefaultPro
```

or the first Pro profile.

So the parameter currently behaves more like **metadata than actual routing control**.

That should either be fixed or removed.

# 4. Cross-synthesis is better, but “deterministic” is too strong

The latest change is a good improvement:

```python
temperature = 0.0
topP = 0.95
```

plus deterministic ordering:

```python
sorted(
    sub_results,
    key=lambda x: (
        str(x.get("title") or "").lower(),
        str(x.get("notebookId"))
    )
)
```

This removes an important source of variation: the order in which concurrent notebook requests happen to finish.

But it does **not** make the LLM output mathematically deterministic.

The provider/model stack can still produce variation.

I would document this as:

> **stable evidence ordering / reduced nondeterminism**

rather than:

> deterministic synthesis

That is a small wording issue, but it matters when you position this as engineering work.

# 5. Your scheduler is surprisingly substantial

`backend/scheduler.py` is not a simple cron queue.

It includes:

- persistent job state
- FIFO scheduling
- multi-profile workers
- cooldown awareness
- restart recovery
- rate-limit retry
- artifact polling
- streaming download
- `download_failed` as a separate state
- retryable jobs
- cancellation
- atomic persistence
- worker release in `finally`

The state model:

```text
queued
scheduled
in_progress
completed
failed
download_failed
cancelled
```

is particularly useful.

Separating:

```text
generation failed
```

from:

```text
generation succeeded, download failed
```

is the sort of distinction that disappears in many student projects.

The regression tests around this are also good.

# 6. Reliability engineering is one of the strongest improvements

There are several concrete engineering decisions I would retain.

### Atomic persistence

`storage.py` uses temporary files plus `os.replace()` rather than directly overwriting JSON.

That is appropriate for your Windows/ReFS environment and protects against partial state writes.

### Restart recovery

An interrupted:

```text
in_progress
```

job becomes:

```text
queued
```

on startup.

That's correct for a durable local queue.

### Windows subprocess handling

The `_run_subprocess_sync()` path explicitly handles:

- `CREATE_NO_WINDOW`
- UTF-8 decoding
- timeout
- stderr/stdout separation
- Windows-specific subprocess behavior

This is clearly based on actual operational problems rather than theoretical design.

### Session recovery

The latest query path detects stale conversation/session errors and retries with a fresh session.

That is another good example of operational hardening.

# 10. Cloud Run is also currently mismatched with the application's authentication model

This is separate from security.

Your local application assumes a machine that has:

```text
NotebookLM CLI
Google account sessions
local profile storage
browser login capability
persistent filesystem
```

For example, `launch_cli_login()` launches a local interactive login process and expects Chrome/browser interaction.

The Docker image, meanwhile, contains:

```text
Python
notebooklm-mcp-cli
FastAPI
application source
frontend
data/
```

but does not provision the user's authenticated NotebookLM profile state.

The application also persists operational state into local files:

```text
data/profiles.json
data/notebooks_cache.json
data/scheduled_jobs.json
data/folder_mappings.json
```

That model is fine for your PC.

It is fundamentally different from a Cloud Run service where the runtime filesystem is not your permanent workstation state and multiple instances can exist.

So the README's:

> “24/7 Hosting on Google Cloud Run”

currently describes something that is **not equivalent to your local authenticated Super-NLM instance**.

This is the largest deployment architecture weakness.

# 11. Reproducibility has a contradiction

You correctly created:

```text
uv.lock
scripts/verify.py
--locked
```

which is good.

But the runtime does something different.

`run.py` performs:

```text
uv tool upgrade notebooklm-mcp-cli
```

at launch.

And the Dockerfile uses:

```dockerfile
pip install notebooklm-mcp-cli fastapi uvicorn ...
```

with no lockfile-based installation.

So you effectively have:

```text
CI
    = locked dependencies

local runtime
    = automatically upgraded CLI

Docker
    = independently resolved pip dependencies
```

That undermines reproducibility.

For a system that you are explicitly documenting as an engineering artifact, this should be tightened.

# 12. There is another smaller reliability problem in account handling

`get_active_profiles()` filters out profiles whose status is `"expired"`.

That means a profile with:

```text
status = "not_logged_in"
```

can still remain eligible for account rotation.

A stronger invariant would be:

```text
eligible for rotation
    =
authenticated
AND healthy
AND not cooling
```

rather than essentially:

```text
not expired
```

Otherwise a newly created account can potentially enter the scheduling/rotation pool before authentication is established.

---

# 13. Error handling occasionally becomes too optimistic

In `ensure_profile_has_access()` the failure path eventually falls back to the equivalent of:

```text
assume access exists
```

after errors.

That is convenient for availability, but it weakens truthfulness of the state machine.

You want:

```text
ACCESS_VERIFIED
ACCESS_UNKNOWN
ACCESS_DENIED
```

rather than turning:

```text
could not verify
```

into:

```text
probably okay
```

Especially when that system is later used by the scheduler and account rotator.

# 19. What I would fix before adding another major feature

The highest-value sequence is now:

### 1. Secure the remote boundary

At minimum:

```text
localhost mode
    → unrestricted

remote mode
    → authentication required
    → restrictive CORS
    → destructive endpoints protected
```

Especially protect profile management, notebook sharing, scheduler controls, and query execution.

### 2. Resolve local-vs-cloud architecture

Pick a clear model:

```text
A. workstation-hosted Super-NLM
```

or

```text
B. genuinely remote service with explicit credential/session architecture
```

rather than presenting Cloud Run as equivalent to the workstation deployment.

### 3. Fix synthesis routing semantics

Either:

```text
synthesizer_profile_id actually controls synthesis
```

or remove that argument.

### 4. Make CI reflect the advertised testing

Turn the standalone synthesis checks into real pytest functions.

Then add at least one integration-level test around:

```text
cross-query → deterministic evidence ordering → synthesis fallback
```

### 5. Make builds reproducible

Use the lockfile consistently and stop silently upgrading the NotebookLM CLI at every launch.

global dispatch counter

Pro filtering
   ↓
explicit exclusions
   ↓
cooldown filtering
   ↓
minimum in-flight load

accounts[current % len(accounts)]

synthesize_with_gemini(question, sub_results)

p.isDefaultPro

# 6. Reliability engineering is one of the strongest improvements

There are several concrete engineering decisions I would retain.

### Atomic persistence

`storage.py` uses temporary files plus `os.replace()` rather than directly overwriting JSON.

That is appropriate for your Windows/ReFS environment and protects against partial state writes.

### Restart recovery

An interrupted:

```text
in_progress
```

job becomes:

```text
queued
```

on startup.

That's correct for a durable local queue.

### Windows subprocess handling

The `_run_subprocess_sync()` path explicitly handles:

- `CREATE_NO_WINDOW`
- UTF-8 decoding
- timeout
- stderr/stdout separation
- Windows-specific subprocess behavior

This is clearly based on actual operational problems rather than theoretical design.

### Session recovery

The latest query path detects stale conversation/session errors and retries with a fresh session.

That is another good example of operational hardening.

# 12. There is another smaller reliability problem in account handling

`get_active_profiles()` filters out profiles whose status is `"expired"`.

That means a profile with:

```text

```

can still remain eligible for account rotation.

A stronger invariant would be:

```text
eligible for rotation
    =
authenticated
AND healthy
AND not cooling
```

rather than essentially:

```text
not expired
```

Otherwise a newly created account can potentially enter the scheduling/rotation pool before authentication is established.

Especially when that system is later used by the scheduler and account rotator.
